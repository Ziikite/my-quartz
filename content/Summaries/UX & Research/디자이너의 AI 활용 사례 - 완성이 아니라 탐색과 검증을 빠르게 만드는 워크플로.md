# 디자이너의 AI 활용 사례 - 완성이 아니라 탐색과 검증을 빠르게 만드는 워크플로

## 한 줄 요약

오늘의집 디자이너의 AI 활용 핵심은 **AI에게 디자인 완성을 맡기는 것이 아니라, 시안 탐색·아이데이션·UT 데이터 세팅·조건부 정책 커뮤니케이션 같은 병목 구간을 빠르게 검증 가능한 형태로 바꾼 것**이다.

## 핵심 메시지

AI는 피그마 안에서 완성도 높은 화면을 바로 그려주는 도구로는 아직 한계가 있다. 하지만 디자인 과정의 병목을 잘게 나누면, AI는 디자이너가 더 빨리 고민하고 더 깊게 검증하도록 돕는 도구가 된다.

이 글에서 특히 중요한 전환은 질문을 바꾼 점이다.

- 기존 질문: “AI가 피그마에 완성된 화면을 바로 그려줄 수 있을까?”
- 바뀐 질문: “디자인 과정에서 시간이 많이 걸리는 병목 구간을 AI로 줄일 수 있을까?”

## 적용 영역별 정리

### 1. AI가 직접 그리기는 아직 어려웠다

Figma MCP와 자체 Figma DS MCP로 AI가 피그마 안에서 직접 화면을 만들게 시도했지만, 완성 용도로는 한계가 있었다.

- 화면 하나를 만드는 데 15~20분이 걸렸다.
- 숙련된 디자이너가 직접 그리면 5분이면 되는 작업도 있어 오히려 느릴 수 있었다.
- Figma는 정적인 화면 단위라 화면 사이의 흐름, 인터랙션, 예외 케이스를 표현하기 어렵다.
- ODS 컴포넌트를 불러올 수 있어도 맥락에 맞게 잘 배치하는 것은 별도의 문제였다.
- 결국 디테일을 잡고 완성하려면 사람의 손길이 필요했다.

다만 다음과 같은 반복 작업에는 도움이 됐다.

- ODS 토큰 미적용 영역에 토큰 일괄 적용
- 화면이 많을 때 공통 수정 사항 일괄 반영
- Athena MCP로 실제 상품 데이터를 가져와 디자인에 적용

### 2. 디자인 초안: Figma Make와 Claude Code로 방향 잡기

초안의 핵심은 하나의 정답을 바로 만드는 것이 아니라, 여러 방향을 펼쳐놓고 팀과 함께 가장 나은 방향을 찾는 것이다.

기존에는 와이어프레임만 2~3일, 구체화된 시안까지는 일주일 가까이 걸릴 수 있었다. AI를 쓰면 이 시간을 줄여 아이디어가 떠오른 당일에 팀 논의를 시작할 수 있다.

#### Figma Make의 강점

- 피그마 안에서 바로 결과물이 나오므로 디자인을 이어서 다듬기 쉽다.
- 플로우 기반으로 화면 간 전환과 흐름을 생성할 수 있다.
- 자주 쓰는 화면을 템플릿화하면 반복 시간을 줄일 수 있다.
- 참고할 피그마 링크와 화면 요소를 구체적으로 알려줄수록 결과가 좋아진다.
- 처음부터 완벽한 결과물을 기대하기보다 여러 번 프롬프트를 주고받으며 다듬는 방식이 효과적이다.

#### Claude Code의 강점

- Figma MCP로 기존 디자인 프레임을 읽어와 실제 동작하는 HTML 프로토타입을 만들 수 있다.
- 구체적인 프롬프트가 없어도 기존 프레임 맥락을 바탕으로 구현한다.
- 피그마 밖에서 동작하는 별도 HTML 결과물이 나오므로, 인터랙션이나 데이터 반영 검증에 적합하다.

#### 인사이트

AI 초안은 바로 쓸 최종안이 아니라 **사고를 확장하는 재료**다. 같은 문제를 다양한 방식으로 풀어주는 것을 보며 힌트를 얻고, 디자이너가 자기 방식으로 디벨롭하는 흐름이 중요하다.

### 3. UT 세팅: 초안 프로토타입을 테스트까지 연결했다

초안 단계에서 만든 프로토타입을 UT에도 그대로 활용할 수 있었다. 별도의 UT용 목업을 다시 만들 필요 없이, 초안 프로토타입에 유저 데이터만 넣으면 테스트로 이어진다.

몰입도 높은 UT를 만들려면 참여자에게 맞는 실제 데이터가 들어가야 한다. 여기서 Figma Make와 Claude Code의 차이가 나타난다.

#### Figma Make 방식

- 유저별 상품 사진과 정보를 직접 찾아서 교체해야 한다.
- 참여자 5명 기준으로 2시간 이상 반복 작업이 필요했다.

#### Claude Code + Athena MCP 방식

- 사내 데이터 조회 MCP인 Athena를 연결했다.
- 유저 ID와 조건을 알려주면 데이터를 조회해 HTML 프로토타입에 한 번에 반영할 수 있다.
- 참여자가 실제로 봤던 상품을 넣을 수 있어 UT 몰입도가 올라간다.
- 유저 5명 데이터 세팅 시간이 **2시간 → 15분**으로 줄었다.

### 4. 정책 커뮤니케이션: 읽는 스펙이 아니라 만져보는 스펙으로 바꿨다

커머스는 조건부 UI가 많다. PDP 가격 ATF만 해도 상품쿠폰, 장바구니쿠폰, 패키지 상품 여부, 수령 여부 조합으로 케이스가 급격히 늘어난다.

기존에는 텍스트나 시안 이미지로 케이스를 정리했지만 다음 문제가 있었다.

- 만드는 사람이 케이스를 빠뜨리기 쉽다.
- 확인하는 사람이 원하는 케이스를 찾기 어렵다.
- 개발/기획/QA가 반복 질문을 하게 된다.

그래서 조건을 직접 토글하면 목업 UI가 실시간으로 바뀌는 **인터랙티브 스펙**을 만들었다.

제작 방식:

1. 피그마에 정리한 스펙을 캡처해 Claude Code에 전달한다.
2. 항목별로 조작 가능한 프로토타입을 만들어달라고 요청한다.
3. “Figma MCP로 이 화면을 읽어서 똑같이 만들어줘”라고 덧붙여 룩앤필을 맞춘다.
4. 새로운 정책이나 조건이 생기면 프롬프트 한 줄로 반영한다.

효과:

- 상품쿠폰, 장바구니쿠폰, 패키지쿠폰 수령 여부를 토글하면 쿠폰할인가, 버튼 상태, 문구가 조건에 따라 즉시 바뀐다.
- 개발/기획/QA가 궁금한 케이스를 스스로 조작하며 확인할 수 있다.
- PDP 가격 정책 개발/QA 과정의 반복 확인 질문이 **0건**이 됐다.

## 성과 수치

- 시안 작업: **3~4일 → 반나절**
- UT 데이터 세팅: **참여자 5명 기준 2시간 → 15분**
- 정책 커뮤니케이션: **반복 질문 → 인터랙티브 스펙으로 0건**

## 관찰 / 인사이트

### 1. AI를 최종 제작자가 아니라 검증 가속기로 둔 점이 좋다

이 사례는 AI에게 “완성된 디자인을 만들어줘”라고 맡기지 않는다. 대신 디자이너가 고민해야 할 방향을 빠르게 펼치고, 실제 데이터를 넣어 검증하고, 복잡한 정책을 만져볼 수 있는 형태로 바꾼다.

포트폴리오에서 AI 활용을 말할 때도 “AI로 화면을 만들었다”보다 “어떤 병목을 찾아서 어떤 검증 흐름으로 바꿨는가”가 훨씬 설득력 있다.

### 2. 디자인 프로세스를 단계별로 쪼갠 것이 핵심이다

이 글은 AI 활용을 하나의 큰 자동화로 묶지 않는다. 디자인 과정을 다음처럼 나눠 각각 다른 AI 활용법을 붙인다.

- 시안 탐색: 여러 방향을 빠르게 펼치기
- 아이데이션: 같은 문제를 다양한 방식으로 풀어보게 하기
- UT 세팅: 유저별 실제 데이터를 프로토타입에 반영하기
- 정책 커뮤니케이션: 조건부 UI를 인터랙티브 스펙으로 만들기

이런 분해가 있어야 “AI를 썼다”가 아니라 “일의 구조를 바꿨다”로 보인다.

### 3. 실제 데이터 연결이 UT의 품질을 높인다

UT 프로토타입에 실제 유저 데이터가 들어가면 참여자의 몰입도가 올라간다. 이는 단순 시간 절감이 아니라 테스트 품질에도 영향을 준다. 특히 커머스처럼 상품 탐색 이력과 개인화 맥락이 중요한 서비스에서는 “현실감 있는 테스트 데이터” 자체가 UX 검증의 중요한 요소가 된다.

### 4. 인터랙티브 스펙은 정책 커뮤니케이션의 좋은 포트폴리오 소재다

텍스트 문서나 정적 시안으로는 조건 조합을 모두 이해시키기 어렵다. 인터랙티브 스펙은 기획/개발/QA가 직접 조건을 바꿔보며 결과를 확인하게 한다. 이는 디자인 산출물을 “보여주는 화면”에서 “의사결정 도구”로 확장한 사례다.

### 5. 디자인시스템이 코드 기반이 아닐 때의 현실적 한계를 인정한다

글은 한계도 분명히 말한다.

- ODS 컴포넌트가 자동으로 입혀지지 않는다.
- 결과물 품질은 프롬프트 작성 능력과 도메인 이해도에 좌우된다.
- 피그마 파일과 AI 프로토타입을 동시에 관리해야 한다.

이 한계를 인정하기 때문에 오히려 실무 사례로 설득력이 있다. AI 만능론이 아니라, 어떤 조건에서 잘 맞고 어떤 부분은 사람이 맡아야 하는지 구분한다.

## 포트폴리오에 적용하는 방법

### 사례 제목 예시

- “AI 프로토타이핑으로 시안 탐색 3~4일을 반나절로 단축”
- “Claude Code와 MCP를 활용한 UT 데이터 세팅 자동화”
- “조건부 가격 정책을 인터랙티브 스펙으로 전환해 QA 반복 질문 0건 달성”
- “완성형 AI 디자인이 아닌 검증형 AI 디자인 워크플로 설계”

### 포트폴리오 구성 예시

1. **문제 정의**
   - 디자인 초안 탐색, UT 데이터 세팅, 조건부 정책 커뮤니케이션에 반복 시간이 많이 들었다.
   - AI가 화면을 직접 완성하는 방식은 느리고 품질도 불안정했다.

2. **접근 전환**
   - AI를 최종 디자인 제작자가 아니라 병목 구간을 푸는 검증 도구로 재정의했다.

3. **워크플로 설계**
   - Figma Make: 피그마 안에서 여러 초안 방향 빠르게 탐색
   - Claude Code: 기존 피그마 프레임을 읽어 HTML 프로토타입 생성
   - Athena MCP: 유저별 실제 데이터를 조회해 프로토타입에 반영
   - 인터랙티브 스펙: 조건부 정책을 토글 가능한 UI로 커뮤니케이션

4. **성과**
   - 시안 작업 3~4일 → 반나절
   - UT 세팅 2시간 → 15분
   - 정책 확인 질문 0건

5. **한계와 후속 개선**
   - ODS 자동 적용 한계
   - 프롬프트 의존성
   - 피그마와 HTML 프로토타입 두 벌 관리 문제
   - 확정된 방향은 피그마에서 사람이 완성하는 흐름 유지

## 바로 써먹을 수 있는 체크리스트

- [ ] AI에게 완성된 화면을 맡기기 전에, 디자인 프로세스의 병목을 먼저 정의했는가?
- [ ] 병목을 시안 탐색, 아이데이션, UT 세팅, 정책 커뮤니케이션처럼 구체 단계로 나눴는가?
- [ ] 각 단계에 맞는 도구를 다르게 선택했는가?
- [ ] AI 결과물을 최종안이 아니라 비교·토론·검증 재료로 사용했는가?
- [ ] 실제 데이터 연결이 필요한 테스트인지 확인했는가?
- [ ] 조건부 UI는 정적 문서보다 인터랙티브 스펙으로 만들 수 있는가?
- [ ] 성과를 시간 단축뿐 아니라 커뮤니케이션 비용 감소로도 측정했는가?
- [ ] AI가 못하는 부분과 사람이 최종 판단해야 하는 부분을 명확히 구분했는가?

## 주의점 / 한계

- AI가 만든 초안은 바로 배포 가능한 디자인이 아니라 검토용 재료로 봐야 한다.
- Figma Make나 Claude Code의 결과 품질은 프롬프트와 도메인 이해도에 크게 의존한다.
- 디자인시스템이 코드 기반으로 정리되어 있지 않으면 AI 결과물에 DS 컴포넌트를 자동 적용하기 어렵다.
- 실제 유저 데이터와 사내 MCP를 연결할 때는 권한, 보안, 개인정보 처리 기준이 필요하다.
- 피그마 원본과 HTML 프로토타입이 분리되면 수정 사항을 양쪽에 반영해야 하는 관리 비용이 생긴다.

## 재사용 문장

> AI 디자인 활용의 핵심은 완성된 화면을 한 번에 뽑는 것이 아니라, 디자이너가 판단해야 할 방향을 더 빨리 펼치고 더 현실적인 데이터로 검증하게 만드는 것이다.

> 좋은 AI 워크플로는 디자이너를 대체하지 않는다. 시안 탐색, UT 세팅, 정책 커뮤니케이션처럼 반복 비용이 큰 구간을 줄여 디자이너가 더 중요한 판단에 집중하게 만든다.

> AI 활용을 포트폴리오에 넣을 때는 도구 이름보다 “어떤 병목을 발견했고, 어떤 단계에 어떤 자동화를 붙였으며, 어떤 수치로 개선됐는지”를 보여줘야 한다.
