## 한 줄 요약

이 글은 “AI로 UX 라이팅을 빨리 했다”가 아니라, **조직의 UX 라이팅 판단 기준을 문서화하고, 케이스를 구조화하고, 인덱스·권한·피드백 루프·피그마 MCP까지 연결해 AI 봇의 품질을 관리한 사례**라서 포트폴리오에 넣을 만한 AI 활용의 깊이를 보여준다.

## 핵심 구조

### 1. 출발점: UX 라이팅의 문제는 문장력이 아니라 판단 기준 부재였다

- 초기에는 요청 건별로 Before/After와 수정 근거를 전달했다.
- 시간이 지나면서 어미, 서비스명 표기, 컴포넌트별 문구 구조 등이 개인 경험에 의존한다는 문제가 드러났다.
- 조직 차원의 합의된 원칙이 없었고, 원칙을 만들더라도 전파가 어려웠다.
- 따라서 AI 도입의 목적은 “문구 자동 생성”이 아니라 **판단 기준의 체계화와 반복 업무 감소**였다.

### 2. 첫 단계: 보이스 앤 톤과 용어집부터 만들었다

- “우리 서비스는 친절합니다” 같은 선언은 실무에서 부족하다.
- 상황별 톤 스펙트럼을 5단계로 나눴다.
  - 1단계: 환영·격려
  - 2단계: 친절·상세
  - 3단계: 중립·명확
  - 4단계: 간결·사실 중심
  - 5단계: 절제·경고
- 이렇게 나누면 AI에게 “이 문구는 4단계로 교정해줘”처럼 구체적으로 지시할 수 있다.
- 용어집은 금지어/권장어, 서비스 고유명사 표기법 등을 담으며, 필자는 봇 품질의 70% 정도를 좌우한다고 느꼈다.

### 3. 도구 선택: Claude Code CLI를 쓴 이유

- ChatGPT나 Gemini에서는 원칙을 프롬프트 안에 직접 넣어야 했다.
- Claude Code CLI는 파일 시스템에 직접 접근할 수 있어, 원칙을 마크다운 파일로 구조화해두고 필요할 때 읽게 할 수 있다.
- 규칙이 바뀌면 프롬프트 전체를 바꾸는 대신 관련 `.md` 파일만 업데이트하면 된다.
- 즉 도구 선택의 핵심은 모델 성능보다 **지식 구조를 파일 시스템 위에 올릴 수 있는가**였다.

### 4. UX 라이터의 사고회로를 5개 영역으로 분해했다

- **페르소나 영역**: 봇의 역할과 태도. “나는 누구인가, 어떤 태도로 유저를 대하는가.”
- **원칙 문서 / Docs**: 보이스 앤 톤, 컴포넌트별 공식, 용어집 등 공식화된 판단 기준.
- **교정 사례 / Cases**: 실제 Before/After와 맥락. 규칙만으로 설명하기 어려운 판례.
- **일별 요약 / Sessions**: 하루 동안의 작업 기억과 반복 패턴.
- **팀원용 설명서 / Guide**: 동료가 이 지식 체계를 어떻게 쓰는지 알려주는 인터페이스.

이 구조는 단일 거대 프롬프트가 아니라, 라이터의 판단을 여러 종류의 지식 저장소로 나눠 관리한 점이 중요하다.

### 5. 케이스 인덱스로 토큰 낭비를 줄였다

- 케이스가 많아질수록 모든 사례를 매번 읽으면 비용이 커진다.
- 그래서 `cases/index.md`를 만들고, 각 케이스에 최소 3개 태그를 부여했다.
- 예시:
  - 문구 유형: `#toast`, `#popup`, `#error`, `#label`
  - 수정 패턴: `#어미통일`, `#간결화`, `#용어교정`
  - 도메인: `#인증`, `#입출금`, `#자산`
- 봇은 인덱스를 먼저 읽고 현재 요청과 매칭되는 케이스만 추가로 읽는다.
- 이는 “많은 지식”보다 **필요한 지식을 찾아 읽는 구조**가 중요하다는 점을 보여준다.

### 6. 품질 관리를 3단계 루프로 설계했다

- **Pre-task / 자기 검증**: 작업 전에 관련 원칙과 유사 케이스를 먼저 찾는다.
- **In-task / 이유 명시**: 교정 근거를 함께 제시한다. 예: “docs/08 팝업 규칙에 따라 명사형으로 바꿨습니다.”
- **Post-task / 후속 질문**: 관련 기획 의도를 확인하고, 필요하면 새 케이스를 저장하고 인덱스에 추가한다.

이 구조 덕분에 팀원은 AI 제안을 블랙박스로 받아들이지 않고 수용/반려 판단을 할 수 있다.

### 7. 반복 패턴을 범용 원칙으로 승격시켰다

- 하루 단위 세션 요약을 만든 이유는 반복 패턴을 찾기 위해서다.
- 같은 원칙이 세션 요약에 3번 이상 등장하면, 개별 케이스가 아니라 범용 원칙으로 올릴 후보가 된다.
- 이때 docs의 원칙으로 승격할지 판단한다.
- 이 루프가 돌면서 봇의 기본 판단력이 장기적으로 개선된다.

### 8. 피그마 MCP와 깃허브로 협업 환경에 연결했다

- 피그마 MCP로 원본 프레임 복제, TOBE 버전 생성, 텍스트 교체, 변경 텍스트 핑크 표시 등을 자동화했다.
- 디자이너는 어떤 문구가 바뀌었는지 시각적으로 바로 확인할 수 있다.
- 깃허브 조직 워크스페이스를 연결하고 `/skill` 방식으로 배포해 팀원이 함께 쓸 수 있게 했다.
- 에이전트보다 스킬을 선택한 이유는 대화 맥락을 유지하며 문구를 함께 고치고, 그 과정을 기록하는 데 유리했기 때문이다.

### 9. 권한 관리로 봇 품질을 지켰다

- 처음에는 누구나 “이거 기록해줘”라고 하면 바로 케이스에 넣었다.
- 검증되지 않은 교정이 판례 풀에 섞이면서 봇 출력이 흔들렸다.
- 이후 권한에 따라 처리 방식을 나눴다.
  - 다른 조직 작업자 요청: Pending Cases에 임시 저장
  - 담당 팀 검토 후: 정식 케이스 생성 + 인덱스 반영 + 세션 요약
- AI 시스템에서도 지식 추가 권한과 검증 절차가 품질 관리의 핵심이다.

### 10. 리소스 50% 절감의 실제 항목

- 원칙 확인: 가이드를 뒤지거나 기억에 의존하지 않고 봇이 관련 원칙을 자동으로 불러온다.
- 유사 사례 검색: 과거 사례 기억 더듬기가 인덱스 매칭으로 바뀐다.
- 피그마 반영: 프레임 복제, 텍스트 교체, 색상 마킹까지 한 번에 진행한다.
- 교정 근거 작성: 원칙 문서를 기반으로 봇이 자동 생성한다.
- 단, 최종 검토와 판단은 여전히 사람이 한다.

## 관찰 / 인사이트

### 포트폴리오에서 중요한 건 “AI를 썼다”가 아니라 “AI가 판단할 수 있는 구조를 만들었다”다

이 사례의 강점은 AI 도구 이름이 아니라, AI가 잘 작동하도록 지식 구조를 설계한 데 있다. 보이스 앤 톤, 용어집, 케이스, 인덱스, 세션 요약, 권한 관리가 모두 하나의 운영 시스템으로 연결되어 있다.

포트폴리오에 AI 활용을 넣는다면 단순히 “ChatGPT로 문구를 개선했다”보다 다음을 보여줘야 한다.

- 어떤 반복 문제를 발견했는가?
- 어떤 기준을 문서화했는가?
- AI가 어떤 자료를 언제 읽게 했는가?
- 결과 품질을 어떻게 검증했는가?
- 팀원이 어떻게 재사용하게 만들었는가?
- 어떤 리소스가 실제로 줄었는가?

### UX 라이팅봇의 핵심 데이터는 프롬프트가 아니라 운영 지식이다

프롬프트를 잘 쓰는 것보다 중요한 것은 외부화된 지식이다. 용어집, 컴포넌트별 문구 공식, 이전 교정 사례, 후속 질문 패턴이 쌓일수록 봇의 품질이 올라간다. 이는 [[AI 디자인 레퍼런스 리서치 자동화 - Codex와 Human-in-the-loop 갤러리]]에서 “검색 범위와 수동 개입 지점”을 설계한 것과 같은 맥락이다.

### Human-in-the-loop가 품질을 만든다

이 글은 최종 판단이 여전히 사람에게 남아 있다고 강조한다. AI는 원칙 확인, 유사 사례 검색, 피그마 반영, 근거 작성 같은 반복 업무를 줄인다. 그러나 문구가 실제 맥락에 맞는지, 사용자 입장에서 자연스러운지는 사람이 판단한다. 좋은 AI 활용은 사람을 빼는 것이 아니라 **사람이 판단에 집중하도록 반복 비용을 줄이는 것**이다.

### 케이스를 무조건 많이 쌓으면 오히려 품질이 흔들린다

좋은 사례만 학습 데이터가 되는 것이 아니다. 검증되지 않은 교정도 들어가면 봇이 나쁜 판례를 따라간다. 따라서 AI 지식 시스템에는 “추가”만큼 “승격/삭제/보류” 프로세스가 필요하다.

## 포트폴리오에 적용하는 방법

### 사례 제목 예시

- “Claude Code 기반 UX 라이팅봇 구축으로 문구 검수 리소스 50% 절감”
- “UX 라이팅 원칙·케이스·인덱스를 구조화한 AI 협업 시스템 설계”
- “Figma MCP와 Claude Code를 연결한 Human-in-the-loop UX Writing Workflow”

### 포트폴리오 구성 예시

1. **문제 정의**
   - 문구 검수 요청은 늘어나는데 판단 기준은 개인 경험에 의존했다.
   - 원칙 전파가 어렵고, 유사 사례 검색과 근거 작성에 시간이 많이 들었다.

2. **기준 만들기**
   - 보이스 앤 톤을 5단계 스펙트럼으로 정의했다.
   - 용어집과 컴포넌트별 문구 원칙을 `.md` 파일로 정리했다.

3. **지식 구조 설계**
   - persona, docs, cases, sessions, guide로 폴더를 분리했다.
   - cases/index.md로 케이스를 태그 기반 검색 가능하게 만들었다.

4. **AI 워크플로 설계**
   - Pre-task: 관련 원칙/케이스 검색
   - In-task: 교정안과 근거 제시
   - Post-task: 후속 질문, 케이스 저장, 세션 요약

5. **협업 연결**
   - Figma MCP로 TOBE 프레임과 변경 표시를 자동화했다.
   - GitHub/skill 방식으로 팀원이 사용할 수 있게 배포했다.

6. **품질 관리**
   - 검증되지 않은 케이스는 Pending에 저장하고, 담당 팀 검토 후 정식 케이스로 승격했다.
   - 반복 패턴은 세션 요약을 통해 범용 원칙 후보로 관리했다.

7. **성과**
   - 원칙 확인, 유사 사례 검색, 피그마 반영, 근거 작성 리소스를 줄였다.
   - 최종 판단은 사람이 하되, 판단에 집중할 수 있는 환경을 만들었다.

### 면접/리뷰에서 강조할 포인트

- “AI를 사용했다”가 아니라 “AI가 읽을 수 있는 지식 구조를 설계했다.”
- “자동화했다”가 아니라 “어디까지 자동화하고 어디서 사람이 판단할지 경계를 설계했다.”
- “프롬프트를 잘 썼다”가 아니라 “원칙과 사례를 업데이트 가능한 시스템으로 만들었다.”
- “결과가 빨라졌다”가 아니라 “반복 업무를 줄이고 판단 품질을 유지하는 루프를 만들었다.”

## 체크리스트

- [ ] AI 활용 사례에 명확한 반복 문제와 병목이 있는가?
- [ ] AI가 따라야 할 기준을 문서화했는가?
- [ ] 프롬프트와 지식을 분리했는가?
- [ ] 용어집, 원칙, 사례, 인덱스 같은 재사용 가능한 자산이 있는가?
- [ ] AI가 답을 내기 전에 관련 기준을 스스로 찾게 했는가?
- [ ] AI 출력에 근거와 파일 출처가 함께 남는가?
- [ ] 잘못된 사례가 지식 베이스에 들어가지 않도록 권한/검수 체계가 있는가?
- [ ] 반복 패턴을 범용 원칙으로 승격시키는 루프가 있는가?
- [ ] 최종 판단을 사람이 하는 지점이 명확한가?
- [ ] 성과가 “시간 절감”뿐 아니라 “판단에 집중할 수 있게 됨”으로 설명되는가?

## 한계 / 주의점

- 기사에는 구체적인 수치 산정 방식이나 실제 Before/After 예시가 제한적으로만 제시된다.
- UX 라이팅 품질은 도메인, 법적 고지, 브랜드 톤에 따라 달라지므로 원칙을 그대로 복사하기보다 자기 서비스 맥락에 맞춰야 한다.
- 검증되지 않은 케이스를 많이 넣으면 봇 품질이 떨어질 수 있다.
- Figma MCP나 Claude Code 사용은 조직의 보안 정책, 파일 접근 권한, 고객 정보 처리 기준을 확인해야 한다.
- 최종 문구 판단은 여전히 사람의 UX 감각과 제품 맥락 이해가 필요하다.

## 재사용 문장

> 포트폴리오에서 AI 활용을 보여줄 때 중요한 것은 어떤 도구를 썼는지가 아니라, AI가 참고할 기준과 사례를 어떻게 구조화했고, 오류를 막기 위한 검증 루프를 어떻게 설계했는지다.

> 좋은 AI 협업 시스템은 사람의 판단을 대체하지 않는다. 원칙 확인, 유사 사례 검색, 근거 작성 같은 반복 비용을 줄여 사람이 더 중요한 판단에 집중하게 만든다.
