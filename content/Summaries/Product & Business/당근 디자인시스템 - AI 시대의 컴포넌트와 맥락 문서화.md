## 한 줄 요약

AI가 UI의 평균 품질을 빠르게 끌어올릴수록, 디자인시스템 팀의 역할은 컴포넌트를 만드는 데서 멈추지 않고 **제품 경험의 판단 기준과 맥락을 사람이든 AI든 읽고 쓸 수 있는 형태로 축적하는 일**로 확장된다.

## 사용자가 남긴 핵심 메모

> 앞으로 디자인시스템은 컴포넌트 문서 + 패턴 문서 + AI가 읽을 수 있는 구조화된 맥락까지 갖춰야 함.

이 메모가 글의 핵심을 잘 압축한다. 글은 디자인시스템이 더 이상 “버튼/입력창/토큰 라이브러리”만이 아니라, 반복되는 제품 판단을 줄이고 AI가 더 나은 화면을 만들 수 있게 하는 **맥락 인프라**가 되어야 한다고 말한다.

## 핵심 구조

1. **디자인시스템은 레고 블록 세트다**
   - 토큰, 컴포넌트, 화면을 만드는 공통 재료를 제공한다.
   - 당근에는 SEED라는 디자인시스템이 있고, 앱의 많은 화면이 이 시스템을 기반으로 만들어진다.

2. **하지만 디자인시스템의 본질은 컴포넌트가 아니라 결정 지원이다**
   - 어떤 화면에 어떤 컴포넌트를 쓸지, 어떤 정보를 얼마나 강조할지, 어떤 행동은 확인을 거칠지 같은 판단을 돕는다.
   - 좋은 디자인시스템은 같은 문제를 만날 때 검증된 선택지를 빠르게 꺼내 쓰게 해준다.

3. **AI는 UI의 하한선을 빠르게 끌어올리고 있다**
   - Lovable, Bolt, v0, Figma Make, Google Stitch, Claude Design 같은 도구가 화면과 코드를 빠르게 만든다.
   - 이제 누구나 꽤 그럴듯한 80%짜리 화면에서 출발할 수 있다.

4. **하지만 80%에서 99%로 가는 것은 맥락의 문제다**
   - 운영 중인 제품의 화면은 앞뒤 흐름, 기존 사용 습관, 브랜드 톤, 밀도, 예외 상태, 접근성, 플랫폼 관습과 연결되어 있다.
   - AI가 좋은 화면을 제안하려면 컴포넌트 이름뿐 아니라 “왜 이 상황에서 이 패턴을 쓰는지”를 알아야 한다.

5. **앞으로의 디자인시스템은 AI가 읽을 수 있어야 한다**
   - 컴포넌트 사용 규칙, 토큰 의미, 카피 톤, 피해야 할 패턴, 좋은 예시와 나쁜 예시, 의사결정 기록을 구조화해야 한다.
   - 문서가 사람에게만 친절한 설명을 넘어 기계가 검색·참조·조합할 수 있는 맥락이 되어야 한다.

6. **경험은 화면 밖에도 있다**
   - 모션, 햅틱, 사운드, 피드백, 실패 안내, 접근성, 상태 처리, 문장 톤, 여백과 밀도까지 디자인시스템의 범위가 확장된다.

## 관찰 / 인사이트

- **디자인시스템의 단위가 컴포넌트에서 패턴으로 올라간다.** 버튼 문서만으로는 “비교가 중요한 상황에서 카드/리스트/테이블 중 무엇을 써야 하는가”에 답하기 어렵다.
- **AI 시대에는 암묵지가 병목이 된다.** 사람 디자이너가 조직 안에서 자연스럽게 익히던 판단 기준을 AI는 모른다. 따라서 암묵지를 문서화·구조화하지 않으면 AI 결과물은 그럴듯하지만 제품답지 않은 화면에 머문다.
- **디자인시스템은 이제 DesignOps이자 Knowledge Infrastructure다.** 컴포넌트 배포보다 더 중요한 일은 반복되는 판단을 기록하고, 팀 전체가 재사용할 수 있는 언어로 바꾸는 것이다.
- **좋은 예시만큼 나쁜 예시도 중요하다.** “이렇게 쓰세요”보다 “이 상황에서는 쓰지 마세요”가 AI와 사람 모두에게 더 강한 제약 조건이 될 수 있다.
- **AI는 디자인시스템 팀의 역할을 줄이기보다 상위 레벨로 이동시킨다.** 화면을 빨리 만드는 일은 자동화되지만, 어떤 화면이 제품 경험에 맞는지 판단하는 기준 설계는 더 중요해진다.

## 실무 적용 예시

### 1. 컴포넌트 문서에서 패턴 문서로 확장

기존 컴포넌트 문서:

- `Button`: 종류, 상태, 크기, 사용법
- `TextField`: 에러 상태, 도움말, 비활성 상태

추가해야 할 패턴 문서:

- 검색 결과가 없을 때의 빈 상태 패턴
- 필터가 많은 목록 화면 패턴
- 되돌릴 수 없는 행동의 확인 패턴
- 저장 성공/실패 피드백 패턴
- 비교가 중요한 정보의 카드/리스트/테이블 선택 기준

### 2. AI가 읽을 수 있는 구조화 예시

```yaml
pattern: destructive_action_confirmation
when_to_use:
  - 사용자의 데이터가 삭제되거나 복구하기 어려운 경우
  - 결제, 탈퇴, 신고처럼 사용자에게 큰 영향을 주는 경우
avoid_when:
  - 되돌리기가 가능하고 영향이 작은 경우
recommended_components:
  - Dialog
  - Button.danger
copy_tone:
  - 짧고 직접적으로 결과를 설명한다
  - 사용자를 겁주기보다 무엇이 사라지는지 명확히 말한다
examples:
  good: "게시글을 삭제할까요? 삭제하면 다시 볼 수 없어요."
  bad: "정말로 진행하시겠습니까?"
accessibility_notes:
  - 키보드 포커스가 확인 버튼으로 바로 이동하지 않게 한다
  - 취소 선택지를 명확히 제공한다
```

## 체크리스트

- [ ] 컴포넌트 문서가 “어떻게 생겼는가”뿐 아니라 “언제/왜 쓰는가”를 설명하는가?
- [ ] 제품에서 반복되는 문제를 패턴 단위로 정리했는가?
- [ ] 좋은 예시와 피해야 할 예시를 함께 모았는가?
- [ ] 토큰의 의미와 사용 맥락을 기계가 읽을 수 있는 구조로 표현했는가?
- [ ] 카피 톤, 접근성, 예외 상태, 실패 상태가 문서에 포함되어 있는가?
- [ ] AI가 만든 화면을 검수할 체크리스트가 있는가?
- [ ] “기존 제품 맥락과 맞는가?”를 판단할 기준이 남아 있는가?
- [ ] 모션, 햅틱, 사운드, 피드백처럼 화면 밖 경험까지 다루는가?

## 내 작업에 가져갈 점

- 디자인시스템/컴포넌트 문서를 볼 때 단순 API나 variant 목록보다 “판단 기준”이 있는지 확인하기.
- AI로 UI를 만들 때 프롬프트에 컴포넌트 이름뿐 아니라 제품 맥락, 패턴 기준, 피해야 할 예시를 함께 넣기.
- 반복되는 UX 결정은 개인 메모로 끝내지 말고 패턴 문서로 승격하기.
- 디자인시스템을 “UI 재료 창고”가 아니라 “제품 경험 의사결정 시스템”으로 바라보기.
