## 한 줄 감상

이 노트는 유저리서치를 “질문을 잘 던지는 기술”이 아니라, **맥락에 맞는 참가자를 찾고 편향을 줄인 프로토콜로 행동을 관찰하는 실무 체계**로 보게 만든다.

## 핵심 요약

스테파니 마시의 『유저리서치』 메모는 사용자 연구의 기본 정의에서 출발해 참가자 모집, 스크리너 설계, 질문 작성, 사전 인터뷰, 리서치 태스크 설계, 참가자가 막혔을 때의 대응, 태스크 후 인터뷰 질문까지 이어진다. 핵심은 사용자의 행위와 동기, 니즈를 특정 맥락 안에서 이해하기 위해 리서치 세션을 최대한 중립적이고 재현 가능하게 설계하는 것이다.

## 기억할 구조

1. **유저리서치의 정의**
   - 사람들이 일상에서 제품을 이해하고 사용하는 데 영향을 미치는 행위, 동기, 니즈를 맥락 안에서 연구하는 것.

2. **참가자 정의와 모집개요**
   - 이해해야 하는 사람이 누구인지 먼저 파악한다.
   - 넓고 많은 표본보다 목표 사용자 몇 명을 정확히 모집하는 것이 중요하다.
   - 모집개요에는 날짜, 장소, 세션 소요시간, 필요한 참가자 수, 시간대, 사례금, 인구통계/성향 조건을 포함한다.

3. **스크리너와 질문 설계**
   - 스크리너 질문은 리서치 목적을 너무 많이 노출하지 않아야 한다.
   - 참가자가 유형을 예측하고 답변을 왜곡하는 상황을 피해야 한다.
   - 질문은 포용적이고 쉬운 언어로 작성한다.
   - 설명적 리서치에서는 중립적인 개방형 질문을 사용한다.
   - 키워드는 제한적으로 사용하고, 규칙을 어겼다면 언제/어떻게 어겼는지 기록한다.

4. **프로토콜 - 사전 인터뷰**
   - 참가자가 과업이나 리서치 분야와 어떤 경험을 갖고 있는지 파악한다.
   - 이후 세션에서 관찰되는 행동을 “왜 그렇게 하는가”와 연결해 이해하기 위한 배경을 만든다.

5. **프로토콜 - 리서치 태스크**
   - 구체적인 태스크는 특정 이슈나 기능을 보고 싶을 때 유용하다.
   - 개방형 태스크는 참가자가 스스로 해답이나 해결책을 찾는 과정을 보고 싶을 때 유용하다.
   - 사전에 정의된 태스크와 사용자에 의해 정의된 태스크를 구분해 설계할 수 있다.

6. **참가자가 막혔을 때의 대응**
   - 질문이 나온 위치를 바로 기록한다.
   - 혼자였다면 어떻게 해결했을지 묻는다.
   - 중요하지 않은 질문은 다음 단계로 넘기고, 중요한 질문은 세션 종료 후 답하겠다고 안내한다.
   - 반드시 도움을 줘야 한다면, 스스로 진행하지 못했다는 사실을 기록한다.

7. **태스크 후 인터뷰**
   - 경험 전체를 어떻게 설명하는지, 기대와 달랐던 부분은 무엇인지, 어려웠던 지점은 어디였는지 묻는다.
   - 한 가지만 바꿀 수 있다면 무엇을 바꾸고 싶은지 묻는 질문은 우선순위와 감정적 임팩트를 파악하는 데 유용하다.

## 관찰 / 인사이트

- **리서치 설계는 모집에서 시작된다.** 참가자를 잘못 잡으면 뒤의 질문과 분석이 아무리 좋아도 결과가 흐려진다.
- **스크리너는 정보 수집 도구이면서 편향 방지 장치다.** 목적을 너무 노출하면 참가자는 “좋은 참가자처럼 보이는 답”을 할 수 있다.
- **질문 문장은 리서치 윤리와 품질을 동시에 좌우한다.** 쉬운 언어, 포용적인 표현, 중립적인 질문은 참가자가 자기 경험을 안전하게 설명하도록 돕는다.
- **태스크 유형은 연구 목적에 따라 달라져야 한다.** 특정 기능의 문제 원인을 보려면 구체적인 태스크, 자연스러운 탐색과 문제 발견이 목표라면 개방형 태스크가 더 적합하다.
- **도움을 준 순간도 데이터다.** 진행자가 개입했다면 실패를 숨기는 것이 아니라, 정확히 언제 어떤 도움을 줬는지 기록해야 한다.

### 스크리너 질문 예시

- 나쁜 질문: “저희 장바구니 이탈 문제를 조사 중인데, 결제 단계에서 불편함을 느끼신 적이 있나요?”
- 좋은 질문: “최근 30일 안에 온라인 쇼핑몰에서 상품을 장바구니에 담은 뒤 결제를 완료하지 않은 경험이 있나요?”
- 이유: 첫 질문은 연구 목적을 노출하고 특정 답변을 유도하지만, 두 번째 질문은 실제 행동 경험을 확인한다.

### 태스크 설계 예시

- 구체적인 태스크: “이 사이트에서 흰색 운동화를 장바구니에 담고 배송비를 확인해 주세요.”
- 개방형 태스크: “곧 여행을 간다고 가정하고, 이 사이트에서 사고 싶은 신발을 찾아보세요.”
- 사용 기준:
  - 특정 단계의 이탈 이유를 보려면 구체적인 태스크.
  - 탐색 방식, 기준, 예상 밖의 문제를 보고 싶다면 개방형 태스크.

### 참가자가 질문했을 때 응답 예시

- 참가자: “이 버튼을 눌러야 하나요?”
- 진행자: “혼자 사용 중이었다면 어떻게 해보셨을 것 같나요?”
- 기록: `결제 단계 CTA 앞에서 멈춤. 버튼 의미를 확신하지 못함. 진행자 질문 후 스스로 클릭.`

## 체크리스트

- [ ] 리서치 목적에 맞는 목표 사용자를 정의했는가?
- [ ] 모집개요에 날짜, 장소, 시간, 인원, 사례금, 조건이 들어갔는가?
- [ ] 스크리너가 리서치 목적을 과도하게 노출하지 않는가?
- [ ] 질문이 쉬운 언어로 되어 있고 포용적인가?
- [ ] 중립적인 개방형 질문을 사용했는가?
- [ ] 질문과 태스크에 키워드가 과도하게 들어가지 않았는가?
- [ ] 구체적인 태스크와 개방형 태스크를 목적에 맞게 구분했는가?
- [ ] 참가자가 질문하거나 막힌 위치를 기록했는가?
- [ ] 진행자가 도움을 준 경우 그 사실을 데이터로 남겼는가?
- [ ] 태스크 후 인터뷰에서 기대, 어려움, 변경하고 싶은 점을 확인했는가?

## 내 작업에 가져갈 점

- 리서치 계획서를 작성할 때 “누구를 이해해야 하는가”를 가장 먼저 쓰기.
- 스크리너를 만들 때 연구 주제를 숨긴 상태에서도 필요한 행동 조건을 판별할 수 있는 질문으로 바꾸기.
- 테스트 중 참가자가 막히면 바로 돕지 말고, 먼저 “혼자였다면 어떻게 했을지”를 물어보기.
- 진행자 개입, 규칙 위반, 태스크 변경은 사소해 보여도 반드시 기록하기.
- 태스크 후 인터뷰 질문 세트를 미리 준비해 모든 참가자에게 일관되게 적용하기.
