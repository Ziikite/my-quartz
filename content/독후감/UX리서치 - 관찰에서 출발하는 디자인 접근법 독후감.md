## 한 줄 감상

좋은 UX리서치는 “무엇을 물을까”보다 “어떤 행동과 맥락을 관찰할까”에서 시작한다는 점을 계속 상기시켜 주는 실무형 방법론 노트다.

## 핵심 요약

이 책/노트에서 반복되는 메시지는 리서치를 의견 수집이 아니라 **행동, 맥락, 태스크, 고충을 구조화해 디자인 의사결정으로 연결하는 과정**으로 다루라는 것이다. 참가자 선정부터 스크리닝, 애스노그래픽 인터뷰, 사용성 테스트, 이슈 우선순위화, 인사이트를 테스트 가능한 디자인 아이디어로 바꾸는 흐름까지 실무자가 바로 써먹을 수 있는 기준들이 정리되어 있다.

## 기억할 구조

1. **데스크 리서치**
   - 이미 존재하는 자료에서 잠재적으로 유용한 단서를 먼저 찾는다.
   - 다만 데스크 리서치는 출발점이지, 사용자 맥락 관찰을 대체하지는 않는다.

2. **참가자 찾기와 스크리닝**
   - 인구통계보다 행동 기준을 우선한다.
   - 디지털 기술 숙련도와 태스크 지식을 높음/낮음으로 나누어 참가자를 분류한다.
   - “자주/가끔”처럼 사람마다 다르게 해석되는 표현보다 실제 행동을 묻는다.
   - 부적합한 후보는 초반 배제 질문으로 걸러내고, 필요한 경우 균형 질문으로 세그먼트 비율을 맞춘다.

3. **디자인 애스노그래피**
   - 사용자의 목표, 현재 수행 방식, 좋아하거나 싫어하는 지점, 어려움, 임시 해결책을 관찰한다.
   - 결과는 보편 진리라기보다 특정 팀/조직의 디자인 의사결정에 쓰이는 맥락적 지식이다.

4. **애스노그래픽 인터뷰**
   - 발견 단계의 고객 인터뷰는 사람들이 `왜` 원하는지 이해하는 데 초점을 둔다.
   - 동기, 활동, 문제를 중심으로 이야기를 끌어내고 구조화한다.
   - 토론 가이드는 질문지를 완벽히 채우는 도구가 아니라 이야기를 이끌어내는 발판이다.

5. **사용성 테스트와 전문가 리뷰**
   - 태스크는 보물찾기식 지시나 자기 생성적 태스크로 구성할 수 있다.
   - 진행자는 말을 너무 많이 하거나 의견/선호를 유도하지 않도록 주의해야 한다.
   - 전문가 리뷰에서도 개인 취향이 아니라 관찰 가능한 기준과 근거로 문제를 판단해야 한다.

6. **우선순위와 디자인 아이디어**
   - 사용자의 기본 태스크 완료를 크게 늦추고 우회 행동을 만들면 심각한 이슈로 본다.
   - 인사이트는 직접 인용, 사용자 목표, 사용자 행동, 고충점, 가능한 디자인 솔루션으로 분해하면 실행 가능한 아이디어가 된다.

## 관찰 / 인사이트

- **리서치 품질은 질문보다 참가자 정의에서 먼저 갈린다.** 잘못된 사람에게 정교한 질문을 해도 좋은 인사이트가 나오기 어렵다.
- **행동 기준 스크리닝이 중요하다.** “30대 여성” 같은 속성보다 “최근 1개월 내 직접 온라인으로 예약을 완료한 사람” 같은 행동 조건이 훨씬 실무적이다.
- **맥락은 답변보다 강하다.** 사용자가 말로 설명하는 니즈보다 실제로 목표를 달성하는 과정에서 보이는 우회, 멈춤, 불안, 반복 행동이 디자인 단서가 된다.
- **진행자의 개입은 데이터 품질을 오염시킨다.** 테스트 중 너무 많이 말하거나 선호를 묻는 순간 참가자는 자신의 행동보다 진행자의 기대를 읽으려 한다.
- **인사이트는 바로 솔루션이 아니다.** 인용문과 관찰을 모아 문제를 정의하고, 그 문제를 가장 작게 해결할 수 있는 디자인 변화를 가설로 만들어야 한다.

## 실무 적용 예시

### 참가자 스크리닝 질문 바꾸기

- 나쁜 질문: “온라인 쇼핑을 자주 하시나요?”
- 좋은 질문: “최근 30일 안에 본인이 직접 온라인 쇼핑몰에서 결제까지 완료한 횟수는 몇 번인가요?”
- 이유: “자주”는 사람마다 다르게 해석되지만, 기간과 행동은 비교 가능하다.

### 발견 인터뷰 가이드 뼈대

- 최근에 해당 일을 마지막으로 한 때는 언제인가?
- 그 일을 하려던 목표는 무엇이었나?
- 실제로 어떤 순서로 진행했나?
- 어느 지점에서 멈추거나 우회했나?
- 어떤 부분이 만족스러웠고 어떤 부분이 불편했나?
- 지금은 어떤 임시 해결책을 쓰고 있나?

### 사용성 테스트 진행자 체크

- 참가자가 막혔을 때 바로 설명하지 않는다.
- “왜 그렇게 생각하셨어요?”보다 “방금 무엇을 하려고 하셨나요?”처럼 행동을 되짚는다.
- 의견을 묻기보다 태스크 수행 과정에서 관찰된 근거를 기록한다.
- 모든 참가자에게 같은 프로토콜과 대본을 적용한다.

## 체크리스트

- [ ] 참가자 조건을 인구통계가 아니라 행동/태스크 경험으로 정의했는가?
- [ ] 스크리닝 질문에 모호한 빈도 표현이 들어가 있지 않은가?
- [ ] 배제 질문과 균형 질문을 구분했는가?
- [ ] 인터뷰 가이드가 “왜/어떻게/어디서 막히는가”를 드러내는가?
- [ ] 사용성 테스트 태스크가 실제 목표와 맥락을 반영하는가?
- [ ] 진행자 발화가 참가자 행동을 유도하지 않는가?
- [ ] 이슈 우선순위가 개인 의견이 아니라 태스크 영향도에 기반하는가?
- [ ] 인사이트를 사용자 목표, 행동, 고충점, 직접 인용, 디자인 가설로 분리했는가?

## 내 작업에 가져갈 점

- 리서치 설계 전에 “이 연구에서 반드시 관찰해야 하는 행동은 무엇인가?”를 먼저 적기.
- 스크리너를 만들 때 속성 조건과 행동 조건을 분리하고, 행동 조건을 우선순위에 두기.
- 인터뷰 후 정리할 때 단순 요약 대신 `직접 인용 → 사용자 목표 → 실제 행동 → 고충점 → 디자인 가설` 형식으로 정리하기.
- 사용성 이슈를 적을 때 “마음에 안 듦”이 아니라 “기본 태스크 완료에 어떤 영향을 줬는가”로 심각도를 매기기.
